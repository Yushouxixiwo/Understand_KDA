A 10-minute primer

让通信与计算
同时忙起来。

通算融合算子把数据切成小块，在同一个算子执行过程中安排通信和计算流水并行，尽量用一边的工作覆盖另一边的等待。

01 / 核心概念

先看懂“融合”指什么

这里的“通算融合”是通信与计算融合。在昇腾文档中常写作 MC²（Matrix Computation & Communication）：原本先执行通信、再执行计算的流程，改为对数据分块，让通信第 i 块时，计算第 i+1 块。

直觉：搬运这一块数据时，别让计算单元闲着；计算另一块时，也别让通信链路空着。目标是隐藏可重叠的等待时间。

“融合”不只是把两个 API 写进同一个函数。关键是依赖关系允许分块、数据缓冲区足够，并且通信和计算确实能并发执行。

03 / 应用场景

哪些工作流值得考虑

Matmul + AllReduce
分布式线性层 / 张量并行。本地计算分片结果后需要跨卡归约。计算后续 tile 的同时，对已就绪的 tile 发起集合通信。
Matmul + ReduceScatter
分片结果并行归约。将部分和的归约与后续矩阵块计算编排在一起，减少独立算子之间的空档。
AllGather + Matmul
先聚合所需输入，再继续消费。能否按 tile 逐步消费已到达的数据，决定了通信能否被计算覆盖。
MoE Dispatch / Combine
专家并行训练与推理。Dispatch 按路由把 token 发往专家；Combine 把专家输出按权重还原、汇总。昇腾 CANN 的 MoeDistributeDispatch / Combine 将路由处理、数据交换及部分后处理结合，以减少 Host 同步并重叠通信和计算。
04 / 性能边界

融合不是自动加速

理想串行耗时 ≈ T计算 + T通信
理想重叠耗时 ≈ max(T计算, T通信) + T启动与拖尾

这个式子给出上限直觉，不是性能承诺。公开的 Ascend C 指导也强调：收益来自通信与计算并行；数据未切分时，MC² 仍可能退化为串行。

两者时间接近

计算和通信有相近的可重叠时长时，隐藏的时间更多。若一边远长于另一边，短的一边很快被完全盖住。

数据可分块且无冲突

当前块通信与下一块计算不能争用同一份未就绪数据；需正确管理 buffer 生命周期、同步点与依赖。

小包的启动成本

块太小会增加提交、同步和调度次数；分块并非越细越好。

拓扑与路由也重要

MoE 的 token 分布、机内/机间带宽、rank 布局会影响路线和通信量。公开的 50% 吞吐提升是特定实现和场景报告，不能当普遍保证。

05 / 学习与开发路线

从问题到可验证实现

先画依赖图

标清每块数据何时产生、何时可发、何时可被计算消费。找出能安全重叠的区间。

量基线

分别测独立通信与计算、端到端串行执行、实际融合实现；固定卡型、规模、shape、精度与并发条件。

设计分块和双缓冲

为块数、块大小、buffer 个数与同步位置做参数化实验，特别关注首块启动和末块拖尾。

验正确性再看时间线

覆盖不同 rank 数、非均匀 token / shape、边界块和异常路径。再用目标平台 profiler 看通信/计算时间线有没有真实重叠。

平台提示：本页讨论的 MC² API、HCCL 与 Ascend C 是昇腾 CANN 生态。NVIDIA CUDA/NCCL 或其他平台也能做通信—计算 overlap，但编程接口、内存模型与支持硬件不同，不能照搬 MC² API。

适合的先修：矩阵计算与 tile 思维、集合通信（AllReduce / AllGather / ReduceScatter）、并行程序中的异步执行与同步。
